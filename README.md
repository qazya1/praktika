# Shaverma Study — учебная система онлайн-заказов для точки быстрого питания

Проект находится в директории [`shaverma-study/`](./shaverma-study).

## Суть проекта

Полноценный, но осознанно упрощённый прототип системы заказов для шаурмичной/кафе, реализующий сквозной цикл **меню → корзина → заказ → обработка сотрудником**. Клиент делает заказ через Telegram Mini App или MAX Mini App, а сотрудники (кассир, повар, директор) обрабатывают его в отдельном веб-кабинете с уведомлениями в реальном времени. Проект построен как демонстрация архитектуры из двух независимых бэкенд-сервисов, разделения ролей и безопасной интеграции с мессенджерами — то есть показывает не просто CRUD, а вдумчивое разделение ответственности между подсистемами.

## Архитектура

Система состоит из трёх независимых сервисов, поднимаемых через Docker Compose, и общей MySQL:

```
frontend/   — клиентский и служебный веб-интерфейсы (Vite + TypeScript)
backend/    — прикладной сервис: FastAPI, единственный владелец данных
manager/    — управляющий сервис: интеграция с Telegram/MAX
mysql       — хранение пользователей, меню, сотрудников, заказов
```

Ключевое архитектурное решение — **разделение прикладной и управляющей логики**:
- `backend` владеет всей бизнес-логикой (авторизация, меню, расчёт суммы, статусы заказа) и ничего не знает о специфике мессенджеров напрямую.
- `manager` отвечает только за коммуникацию с Telegram/MAX Bot API (уведомления сотрудникам, выдача ссылок запуска Mini App) и не имеет прав менять заказы.
- Сервисы общаются по HTTP с внутренним заголовком `X-Internal-Key`, при этом сбой мессенджера **не отменяет** уже созданный заказ — важное решение для отказоустойчивости.

## Технологический стек

- **Backend**: Python, FastAPI, SQLAlchemy, MySQL, Pytest
- **Manager**: Python, FastAPI (отдельный лёгкий сервис для ботов)
- **Frontend**: TypeScript, Vite, HTML/CSS (адаптивная вёрстка без тяжёлых фреймворков)
- **Инфраструктура**: Docker, Docker Compose (единая команда `docker compose up --build` поднимает всё окружение)

## Функциональность

**Клиентская часть:**
- Просмотр меню с категориями и изображениями блюд
- Корзина и оформление заказа
- История заказов пользователя
- Авторизация через криптографически проверяемый `initData` (Telegram Mini Apps / MAX Mini Apps)

**Служебная часть (кабинет сотрудников):**
- Отдельная авторизация по логину/паролю (не через мессенджер)
- Ролевая модель: `cashier` (перевод `new → cooking`, `ready → completed`, отмена), `cook` (`cooking → ready`), `director` (все переходы и отмена)
- Разграничение допустимых переходов статуса заказа на уровне бэкенда
- Уведомления сотрудникам о новых заказах через Telegram/MAX

**Данные**: 5 таблиц (`users`, `staff`, `products`, `orders`, `order_items`), причём в `order_items` хранится снимок названия и цены на момент заказа — типичное для e-commerce решение, защищающее историю от изменений в текущем меню.

**API** (7 основных эндпоинтов): `GET /api/menu`, `POST /api/auth/messenger`, `GET/POST /api/orders`, `POST /api/staff/login`, `GET /api/staff/orders`, `PATCH /api/staff/orders/{id}/status`.

## Безопасность

Особое внимание уделено проверке подлинности данных из Mini Apps: бэкенд принимает только исходную строку `initData`, самостоятельно сортирует параметры, формирует строку проверки и сверяет HMAC-SHA256 подпись с токеном бота, дополнительно проверяя срок действия (`auth_date`). Небезопасный объект `initDataUnsafe` для авторизации принципиально не используется. Dev-режим авторизации (`DEV_AUTH=true`) явно отделён от продакшена.

## Тестирование

Функциональные тесты на Pytest покрывают ключевые сценарии: загрузку меню, авторизацию клиента, оформление заказа, вход сотрудников и допустимые/запрещённые переходы статусов заказа. Дополнительно проверены типизация фронтенда (`tsc --noEmit`) и компиляция Python-кода обоих сервисов.

## Осознанные ограничения

В проекте намеренно нет платежей, QR-кодов, бонусной системы, рефералов, поддержки нескольких заведений, фоновых очередей и расширенной аналитики — это сознательное решение сфокусироваться на демонстрации архитектуры и базового цикла заказа, а не на воспроизведении полноценного коммерческого продукта.

## Быстрый запуск

```bash
cd shaverma-study
cp .env.example .env
docker compose up --build
```

Подробности запуска, демо-учётные записи сотрудников и остальную документацию см. в [`shaverma-study/README.md`](./shaverma-study/README.md) и папке [`shaverma-study/docs/`](./shaverma-study/docs).
